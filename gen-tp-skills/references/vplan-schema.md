# 场景 vPlan 的 13 字段合同

本文件是本包场景数据字段规则的唯一来源。保留原 13 字段语义及工作 Markdown 的工具兼容性；**一行是一个主验证目标，适用于 base、Cross 和 Scenario；检查项与覆盖维度不自动成为新行。** 场景数据只维护一份，附录补充和映射。交付格式由用户选择；Excel 的多 Sheet、英文列名映射见[格式说明](output-formats.md)，不要求交付中文 13 列 Markdown。

## 字段与职责

表头和顺序固定，为读取兼容保留历史字样 `(Optional)`；它不表示第 10 字段可省略。自 v2.4 起所有新建/修订点均填写直接用例激励，旧表迁移见[迁移规则](migration.md)。字段 2–4 无须用满。

| 序号 | 表头 | 场景写法 |
|---|---|---|
| 1 | 测试需求 | 新计划为 Register Access / Config Space / Dynamic Input / Performance / Cross / Scenario 之一；旧分类仅兼容读取，迁移见大纲 |
| 2 | 测试子需求(L1) | 可识别的业务场景族或独立专项，非空；必要时与第1列共同体现模式和业务通路 |
| 3 | 测试子需求(L2) | 必要时细分，无则 `-` |
| 4 | 测试子需求(L3) | 必要时细分，无则 `-`，不为用满层级而填参数 |
| 5 | 测试点名 | 唯一，匹配 `[a-z][a-z0-9_]*`，建议 `<dut>_<scenario>` |
| 6 | 测试点描述 | 最多 200 字符，概括主目标、关键业务条件和外部预期；长前序放附录 |
| 7 | 需求ID(s) | 来源 ID 或声明过的本地 ID，多个用逗号分隔；精细映射见来源附录 |
| 8 | 关联用例名称 | 新点 `待反填`；已有真实关联保留，支持多对多，不要求一个场景一个用例 |
| 9 | 功能覆盖率描述(Optional) | `[cg]/[cp]/[p]` 时写设计要求的覆盖维度和所需证据；采样实现未知可标待设计；`[t]` 可写辅助覆盖，无则 `-` |
| 10 | 直接用例激励描述(Optional) | 所有点必填必要配置及值/约束、发起接口与请求、推进顺序、预期和结束条件；未知项就地标 `需要 check`。详见[激励写法](stimulus-description.md) |
| 11 | 环境检查说明 | 先写完整设计判据，再单独标实施状态，如check待设计、仅部分可检查或暂无法准确check；不能用平台能力改写预期 |
| 12 | 度量测试点覆盖 | 单个主度量 `[cg]` / `[cp]` / `[p]` / `[t]` 加目标 |
| 13 | 标签 | DUT/设计基线版本；未知为 `待确认` 并记录问题，不以技能版本冒充 DUT 版本 |

空值用 `-`，新用例未知用 `待反填`。中文说明、英文小写标识符；表内管道转义为 `\|`，换行用 `<br>`。复杂步骤、代码、多个维度或检查编号放入按测试点名索引的场景补充。

## 主度量与混合策略

| 类型 | 规划目标示例 | 具体目标示例 | 第 9 / 10 列 |
|---|---|---|---|
| `[cg]` | `[cg] 待设计:完成协调` | `[cg] env.cov.completion_cg` | 维度、必要交叉、采样和完成标准 / 必要激励与预期 |
| `[cp]` | `[cp] 待设计:长度边界` | `[cp] env.cov.length_cg.length_cp` | bins、采样事件及有效检查条件 / 必要激励与预期 |
| `[p]` | `[p] 待设计:握手稳定性` | `[p] demo_if.stable_p` | 边界性质、非空触发及完成覆盖 / 必要激励与预期 |
| `[t]` | `[t] 待反填` | `[t] demo_recovery_vseq` | 辅助覆盖或 `-` / 必要激励与预期 |

选择一个主度量便于现有工具处理，**不代表场景只能用一种激励或检查技术**：

- 所有主度量的场景都在第 10 字段写必要配置、外部操作和预期；可以先定向建立资源状态，再随机变化合法参数，不为了记录步骤改成 `[t]`。
- 第 9 与第 10 字段不互斥：`[cg]/[cp]/[p]` 两者均必填；`[t]` 第 9 字段可填辅助覆盖或 `-`，第 10 字段仍必填。旧消费方若假定互斥，需要显式报告兼容差异。
- 一个场景需要多个辅助覆盖/属性时，在附录逐项说明，主度量的完成判据必须包含这些必要证据；不能让一个小属性代表整个复杂场景。
- 度量不自动决定 Random/Direct；不因采用 `[p]` 就强制随机，也不因有顺序描述就强制定向。

执行后认定覆盖成立需要：场景条件确实发生、要求的合法维度/交叉已命中、相关检查有效且通过、达到规定结束条件。这是覆盖闭合要求，不是建立测试点的门槛；实施方法不明、无法准确check时仍保留完整测试点。检查负向结果时确认未出现禁止事件及后续恢复。激励发出、采样一次或属性未触发均不足以宣称覆盖。

具体目标可为商定的规划路径；在能力交接中标 `待设计/规划/已核对`。脚本不验证路径存在，更不验证覆盖证据。交接校验拒绝字段 12 占位，具体行为见[交付说明](delivery.md)。

## 工作 Markdown 结构与统计

必需内容是验证边界与依据、统计、场景及需求来源。以下章节是内部校验或选中 Markdown 时的结构；Excel 将测试点按六类分 Sheet、结构化规格问题及 TP 阻塞关系放入专用 Sheet、其他元信息及附录保存在 Plan Notes，不强制再交付 Markdown。场景组织、场景补充、范围处置、规格缺口和能力交接按实际内容使用，不为凑模板而全部展开。

- 头部包含唯一的 `> 总测试点数：N`。N统计全部主表规划场景，包括激励/check待设计、暂无法准确check及有明确目标但规格待确认的点；不等于当前可执行数量。不另计检查项、bins或同一测试点关联的缺口，纯问题和确属范围外的结构转交项不重复计数。
- `## 验证边界与依据`：DUT 范围、外部接口、输入保证、采用的规格基线和文档限制。
- `## 场景组织`：说明模式、典型业务通路及结束方式；复杂分支可列“模式—业务—分支—场景名”索引。确保最小合法业务可定位，避免复制主表或只列ACK/资源等环节。
- `## 测试点统计`：两列 `测试需求/测试点数量`，各类数量及 `合计`。
- `## 测试点汇总表`：唯一的 13 列主表，行内无实际换行、无合并单元格。
- `## 场景补充`：按需提供每点的前序、维度、检查项和结束事件；主表已表达清楚时不重复。
- `## 需求来源`：ID → 文档、版本、具体章节 → 场景的检查项/覆盖维度。来源 feature 太宽时补充支撑预期的细节章节。
- `## 范围处置`：记录依据设计职责/约束确认的范围外或不适用项；平台缺能力、不会构造、无法精确check不能成为移出主表的理由。需要辅助证明的业务测试点保留原目标并关联实施需求。
- `## 规格缺口`：新计划使用[大纲](tp-outline.md)规定的九列问题表；一个问题可关联多点，纯问题填 affected_tp_ids 为 `-`。即使无问题也保留表头。
- `## base 适用性`：固定列 `category / disposition / basis`，四类 base 各一行；disposition 为 `有测试点`、`规格待补充` 或 `不适用`，basis 写具体设计依据/缺少资料。
- `## 测试点状态`：可选两列 `TP_ID / lifecycle_status`；未列出的点默认 draft，open 问题关联点不能标 reviewed/complete。状态含义见大纲。
- `## 能力交接`：按需交接检查/采样/驱动需求及已知限制；不要求调研现有平台，是测试点提出的能力需求，不能反向裁剪测试点。标明所需判据与当前可检查部分的差距。

新计划头部增加 `> 分类体系：base-cross-scenario`；base 适用性与规格缺口是该分类体系的必需结构。没有内容的其他可选附录省略。共用前序和配置可集中为具名基线，每行仍须保留专属值、接口请求、预期与结束条件。复杂长步骤放附录，不在附录重复主表已有内容。能力相同的场景可分组交接，但需明确适用点及例外。来源映射保持必要的精度，不复制规格全文。主表与附录各有唯一职责，模板不是篇幅目标。

## 修订与下游边界

仅修改某点时保持其他 ID、用户描述和关联用例。场景合并按[迁移规则](migration.md)保留原点去向、有效判据、维度和已有真实关联；无法确定关联归属时保留待复核说明，不清空历史记录。

TC 生成/回填关联用例（工作表第 8 字段、Excel related_testcases）不自动获得度量目标（第 12 字段、coverage_strategy_mapping）修改权。内容更新后同步用户选中的各格式。保留工作字段只保证本包兼容，不表示旧 TC 消费方支持多 Sheet、英文列名、场景粒度、多对多或混合策略。
