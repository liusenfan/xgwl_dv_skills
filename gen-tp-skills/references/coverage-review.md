# 基础与关系检查

用于基础扫描和交付前补漏。顺序为：业务骨架 → 基础对象与关系扫描 → 详细 Scenario → 双向补漏。扫描完成表示范围内对象、定义及关系均已检查，缺口已有去向；不要求所有规格问题已解决。

## 1. 范围内逐项扫描

以本次指定的有效设计资料建立紧凑清单，核对四类 base：寄存器访问、配置、动态输入、性能。记录 `对象/关系 | 来源ID | TP/检查项/维度或处置`，可直接扩展需求来源映射，不重复维护第二份 TP 表。

- 不因对象未出现在当前典型业务中而遗漏；只分析指定功能时，检查该范围及必要依赖，声明局部分析，不强制生成全模块 TP。
- 对象及其已定义语义须有去向：正式 TP、检查项、覆盖维度，或带设计依据的不适用/范围处置。已有目标但规格未明确的，保留 TP 并关联问题；纯问题不能制造空 TP。
- 清单逐项不等于 TP 逐项。多个同构寄存器可归组，但对象、各自有效位和预期规则必须可定位；同一目标的等价值可作为维度。
- Register Access 的扫描对象为设计规定的寄存器属性；APB时序、等待、传输规则和协议错误不自动形成该页测试点，边界见[测试点大纲](tp-outline.md#register-access-的模块级边界)。
- 基础扫描与业务细化可往返；局部缺口不阻挡独立场景，未决项不支持宣称对应语义已完整。

## 2. 先归并定义，再判断缺失

对同一对象，检查寄存器表、功能章节、接口、模式和例外条款等相关位置。身份、所属对象及适用条件明确对应时归并互补定义，保留每条语义的来源。

- 不凭同名合并，不把不同模式、版本或对象的定义拼成一个确定结论。
- 规格优先级按用户基线或文档明确替代关系；冲突保留双方定位及工作口径，不因 LLD 更细或日期更新而自动覆盖其他来源。
- 资料中找不到或无法唯一对应的内容记录具体问题；不读 RTL、平台实现或凭经验填空。

## 3. 系统扫描多对象关系

逐项阅读配置、输入接口、业务和资源定义中涉及其他对象的条件，并检查独立描述的关系：

| 关系 | 要保留的内容 |
|---|---|
| 配置×输入 | 选择、匹配、互斥及条件对应的结果 |
| 模式×业务 | 适用条件、执行/跳过/拒绝及结束行为 |
| 业务×资源 | 取得、等待、占用、释放及恢复条件 |
| 并发业务 | 顺序、身份隔离和相互影响 |
| 请求/完成/返回 | 身份关联、先后与次数约束 |

先保留参与对象、完整适用条件和关系/结果，再按主目标放入已有 TP 的检查项、覆盖维度或独立 Cross/Scenario。通用规则可引用复用，场景专有规则直接写入该 Scenario，不为关联而虚构基础 TP。

关系不限于 Config/Dynamic 参数；外部握手、ACK、资源返回及反压按行为分析，不因为有信号就自动列点。多个对象同时出现不自动成为 Cross，不做无依据的笛卡尔积。内部信号只辅助理解，不因此成为黑盒外部输入。

## 4. 取值对应行为，分区覆盖补漏

依据设计列出取值范围、枚举含义、边界及行为分区，明确每个分区对应的预期。完整性是已定义语义无遗漏，不等于穷举全部数值或为每个值建立 TP/bin。

- 同行为的等价值可归组；执行、跳过、重生等不同路径须分别保留判据及完成证据。
- 值的合法性或行为依赖模式/其他参数时保留完整条件，关联第 3 节的关系；不能把条件成立时的结论写成无条件行为。
- 边界及代表值注明是设计规定还是策略选择。不固定“中间值”或统一枚举阈值替代风险分析。
- 只有编码清单、没有对应行为，不能宣称该行为已分析完整。未知响应关联问题，不猜报错/忽略，也不删除整个目标。

示例（仅说明分区方法）：若设计规定 0 跳过、1–8 执行、9–15 为保留编码且响应未定义，则分别保留跳过判据、执行数量及边界覆盖、保留编码待确认项，不能只写“覆盖 0–15”。

场景中固定、受约束、可自由变化及不参与的参数，按[必要激励规则](stimulus-description.md)表达；不提及不等于默认值。

## 5. 负向测试不等于 illegal bins

分别判断输入是否合法、设计如何处理、覆盖模型如何记录。需要主动构造并验证报错/忽略/拒绝等已定义响应的非法、保留或不支持输入，应设置可正常统计的覆盖目标；不因名称带“非法”就归入 `illegal bins`。

只有设计要求某状态或组合在指定观察条件下绝不能发生时，才明确其禁止行为及判据；是否使用 `illegal bins` 由后续覆盖实现决定。TP 阶段不强制编写 SV bins。

负向条件命中不等于验证通过，还需检查规定响应和适用的恢复行为。外部环境不得发送某组合，并不能推出 DUT 必须自动检测或报错；响应未知则标规格问题。

## 6. 性能的对象、条件、口径与判据

| 内容 | 写清什么 |
|---|---|
| 测量对象 | 请求接收延迟、业务完成延迟、吞吐量等公开指标 |
| 测量条件 | 模式、负载、并发、外部背压及相关环境条件 |
| 测量口径 | 起止事件、统计对象、单位，以及适用的平均/最大值或稳态窗口 |
| 合格判据 | 设计阈值、公式或约束及来源，与测量口径对应 |

“每周期发射一条”须说明适用条件、接口的接收事件、启动/停顿是否计入，不能只写“吞吐达到 1”。缺少阈值或口径仍保留已知目标并关联问题；未解决的设计判据不能以策略看门狗代替。

条件与测量步骤放必要激励，设计判据放目标和检查说明，避免重复字段。预热长度、测试时长等验证选择注明策略性质；计数、时间戳、断言等方法按证据需要选择，不按类别固定。

## 7. 交付前双向核对

从设计对象和关系检查是否有去向，再从每个 Scenario 检查其必要配置、输入及约束是否充分。已有问题明确关联；有设计目标就保留正式 TP_ID、完整条件、预期和来源。

表达式、覆盖模型或脚本不能承载时，可先用明确文字、公式或分支表表达，并在能力交接记录转换待办；不得转成不计数候选或用较弱条件替代。清单只是覆盖分析依据，不证明仿真或覆盖已经完成。
