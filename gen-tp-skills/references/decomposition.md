# 系统黑盒场景分解决策

## 1. 先确定什么在黑盒里面

写明 DUT 包含的组件、外部参与者、可驱动/观察接口、公开状态以及环境保证。验证级别相对于这个边界：TS 整体的内部 TG 信号不能因为写在 LLD 就当作系统接口；若更大系统把 Core 也包含进去，则 TS→Core 命令可能已不可见，需要重新定义观察结果。

先建立简短的设计理解：业务入口和出口、主要生命周期、身份关联、资源取得/释放、独立并发路径。内部结构可帮助解释风险；Scenario 内按业务目标组织，完整计划还须逐项完成[六类大纲](tp-outline.md)，不能省略 base 和 Cross。协议转换器、控制调度器与数据处理系统具有不同的外部结果，不套同一套数据比对模式。

## 2. 筛选规格并处理差异

将相关内容区分为：

| 类型 | 处理 |
|---|---|
| 明确的外部需求 | 提取条件、输入、结果和适用模式，形成场景依据 |
| 内部实现机制 | 提炼相关业务行为及设计约束；业务目标保留，纯结构证明依据验证范围另行追溯 |
| 系统输入保证 | 作为合法激励约束，例如 ACK 顺序一致、容量不超额；不反向推导硬件应自动防护 |
| 旧版、删除或疑似模板遗留 | 记录排除依据或待确认项，不自动生成测试点 |
| 未定义或冲突行为 | 保留来源差异、影响范围和最小澄清问题，不猜一个响应 |

优先级来自用户指定的规格基线或明确替代关系。日期较新、章节更细、名称为 LLD 都不足以单独证明权威性。可继续使用无冲突部分；不要把有少量缺口的整个功能标成不可验证。

来源中的“当前 RTL”描述仍是文档陈述，不等于经过独立验证的功能承诺。先判断它是否定义本次边界行为；不要直接照着实现结构复制检查器。测试点及预期只依据设计文档，验证方案用于承接实施，不新增、裁剪或替代设计要求。生成测试点无需读取现有平台或检查driver/checker是否已实现。

## 3. 先建立模式下的业务骨架

在读完有效规格后，先回答四层问题，再进入场景/检查项/维度的填写：

| 层级 | 要识别的内容 | 组织作用 |
|---|---|---|
| 工作模式 | 模式如何进入，身份如何建立，怎样结束 | 入口或生命周期不同的模式分别梳理；只有结果和检查语义一致时才作为同一场景的模式维度 |
| 业务通路 | 外部发起什么业务，DUT沿哪些可见接口输出，等待哪些返回 | 为每条典型通路建立可独立验收的场景族 |
| 业务分支 | 哪些属性决定执行、跳过、旁路、恢复或重生 | 明确各分支的应有和禁止输出；结果不同的路径分别记录完成证据 |
| 规模与时序 | 最小业务、任务链、多用户、并发、返回先后、反压 | 在基础场景上扩展有意义且可达的组合 |

“通路”以外部业务及接口行为描述，不要求复刻内部数据流图。工作模式、任务类型和 Reissue 等控制属性不要混成同一层枚举，也不默认做全笛卡尔积；不适用/未知组合分别说明依据。

### 基础闭环先有明确落点

对每个适用的典型业务，明确 **合法前置条件 → 业务启动 → 预期输出/执行 → 所需完成 → 退出、资源释放或下一轮**。纯 Skip、拒绝等分支也应定义不产生哪些输出，以及后续如何结束或恢复。最小合法业务可作为独立基础场景，任务链场景验证组合与阶段衔接。

不能仅把“单 Task”写进配置用例的“链长=1”维度，就认为已规划了单 Task 操作；也不能仅靠通用 ACK、仲裁、Credit、退休点的集合，推断某条业务闭环已经有独立检查与覆盖。单 Task 必须先确认在所选模式/类型下可合法启动，不能为满足目录而绕过必要前序。

业务目录可直接通过主表分类和场景名体现。只有多模式/多分支难以看清时，才补一张紧凑的“模式—业务—分支—场景名”对应表；它只作索引，不复制第二份测试点表。新计划第一层采用六类大纲，Scenario 的子分类按模式和业务组织；旧表迁移时在子分类或映射保留原业务层级，重组分类需在授权范围内。

### 扩展顺序与专项检查

基础闭环明确后，再考虑多 Task、多用户、跨业务并发、反压、资源等待/恢复及异常。模式改变入口或结束行为时，分别定义预期，不能只采一个 mode bin。业务属性改变执行集合时，在同一场景中写清分支判据及分别成立的覆盖目标；若主目标、合法前序或恢复过程独立，则拆成独立点。

接口保持、配置失败修复、多方向原子取得等可独立验收的性质仍可单列。它们与业务场景共享检查能力并建立关联，不替代典型业务规划；业务跑通也不自动证明所有资源和协议性质。已有 DV MAS 的组件划分用于承接能力，不决定业务目录；不能因平台仅实现某些检查器就遗漏其他合法业务。

TS 的具体层级和通路示例见 [TS 业务组织](../examples/ts-reframing.md)。其他 DUT 应从自身规格提取业务，不能照搬 Normal/Special 等 TS 名称。

## 4. 三层内容模型

### 场景测试点

一行代表一个主验证目标，以及能够触发和判定它的业务条件。必须说清：

- **目标：** 主要防止什么外部错误，例如过早推进、资源多扣、身份串用。
- **前置条件：** 合法配置、业务模式、已发生事务和资源欠账如何建立。
- **外部事件：** 发什么请求，控制哪些完成、反压或归还事件。
- **预期和结束：** 哪些输出应出现/不应出现，以什么事件确认场景结束。

需要一个初始事务才能验证协议稳定性，也可以构成完整黑盒场景；不是每点都必须从整机上电跑到全部业务结束。

### 检查项

服务于场景主目标的判据可在同一行列为 C1、C2 等；只有内容较多或需要精确追溯时才编号。例如完成协调的检查项包括“未收齐不推进”“收齐后正确推进”“身份不串用”。不要因为它们有不同断言或 checker 就拆成多行。

检查项必须指向可见输出、公开状态或可由已接受输入推导的预期；“SCB 正确”“内部状态正确”不是判据。预期来源独立于 DUT 结果，不用实际输出反过来定义应有结果。

### 覆盖维度

参数、实例、事件先后、返回间隔、合法边界和竞争组合，在检查语义可统一表达时作为场景维度。模式及业务分支按第 3 节判断，不能因它们由一个字段控制就自动降为取值覆盖。需要说明取值/代表性分区和有意义的交叉；排除不可能或非法组合应有依据。

维度数、场景数和循环次数由需求与风险决定。测试策略选择的重复次数、随机种子或观察超时需标明是策略，不写成设计承诺。

## 5. 拆分、合并和转交

| 判断 | 决策 |
|---|---|
| 同一目标，只改变合法值、同构实例、先后顺序或负载 | 优先作为维度，关联检查留在同一场景 |
| 多项外部检查共同证明一个目标 | 可合并；不要求所有检查完全同义 |
| 主目标、输入合法性、预期响应或恢复流程明显不同 | 通常分开，或在父类下保留独立场景 |
| 基础业务闭环被拆散到配置、ACK、资源和退休等环节 | 建立可独立验收的业务场景，复用相关判据；不以多个环节分别通过代替业务闭环覆盖 |
| 属性取值导致业务执行集合或生命周期改变 | 显式列出各路径判据和分别完成的证据；按目标/前序差异决定分支或独立点 |
| 合并会掩盖需要单独建立条件并证明的风险 | 保留独立场景，例如多方向原子申请与方向重复使用 |
| 只描述内部状态、位图、FIFO 指针或流水级 | 区分业务要求和纯结构证明；前者保留完整目标，后者按设计范围另行追溯；不能用平台观察不足作范围判断 |
| 只有疑问，无法识别任何有设计依据的验证目标 | 仅列规格问题；已有设计目标但响应未定的点仍留主表并关联问题 |

禁止按每个字段取值或内部实现分支机械生成一行，也不能把所有功能压成一个“综合随机压力”点。Register Access 的独立访问属性、Config Space 的独立配置语义可按寄存器/字段列点，同构实例可归组；不得以场景化为由省略必查 base 目标。压力场景可补交互风险，不能替代各主目标的定向判据或可识别覆盖目标。

合并后要求每个原有有效需求、检查和风险都可找到去向。测试点行的合并与多个测试点共用一个用例分别处理，详见[迁移规则](migration.md)。

## 6. 设计目标与实施能力分开记录

**列点依据是设计要求，不是当前能否驱动、观察、准确check或实现覆盖采样。** 先完整写出场景及预期，再记录已知的实施缺口；不要求分解阶段设计出可运行的激励和checker，也不因尚未找到方法就漏写该点。

| 情况 | 测试点处理 | 实施或规格说明 |
|---|---|---|
| 设计要求明确，平台无驱动/检查能力或能力未知 | 保留主表完整目标，计入规划总数 | 写激励/检查待设计；不需要先调研平台再列点 |
| 设计要求包含并发、竞争或特定时序，当前无法确认精确条件是否发生 | 保留该条件、完整预期及覆盖目标 | 标条件命中证明/精确check待设计；可记录已有部分检查，但不能以它替换原要求或宣称覆盖 |
| 设计要求明确，尚不知道如何从外部建立前序 | 保留场景；描述设计规定的前置状态和行为 | 标激励构造待设计；缺协议资料则关联规格确认项，不把尚未找到方法推断为不可达 |
| 设计目标明确，但验证边界或接口观察方式未确定 | 保留目标、来源和候选模式，标边界待确认 | 观察点及能力归属待方案处理，继续分解其他目标 |
| 设计存在冲突，或目标明确但预期阈值/响应欠定义 | 主表保留设计目标，关联规格缺口 | 判据未决部分写待确认，不补造行为；与平台能力不足分开 |
| 设计明确禁止某组合，或依据设计约束严格证明不适用 | 写明设计条款及推导，保留处置记录 | 这是规格/范围结论；仅凭平台无法生成、无法观察或模型不会构造，不能采用此结论 |

检查说明分开表达“设计应满足的判据”和“当前能检查到哪里”。前者不随平台限制削弱；后者可为未设计、部分可检查或暂无法准确check。不要求新增固定列，可写在环境检查说明和能力交接中。规划数量、可执行数量、已检查和已覆盖数量必须区分，不能只统计能跑的测试点。

纯内部结构要求（例如FIFO指针编码）按设计验证范围另行追溯；包含外部业务目标的场景仍在主表，不能因需要辅助观察或白盒协作而整体转交删除。后续可研究更准确的模型、观测或辅助检查手段，本技能不预先指定实现方案。

执行阶段仍须有充分证据才能标已覆盖：没有命中证明或准确检查时如实保留未闭合状态。无设计延迟上限时，测试看门狗超时不能直接当作违反性能规格。**保留测试点不等于承诺当前平台已能验证它。**

## 7. 在业务骨架上补漏

完成第 3 节的模式和业务骨架后，用下表补漏。这些是设计检查角度，再按六类大纲归类；四类 base 必须逐项评估。只有设计确认没有该项功能时才可标不适用；资料不明标规格待补充，平台能力不足不允许跳过。避免仅有专项而缺少 Scenario 的业务闭环。

| 主题 | 黑盒关注点 | 粒度提醒 |
|---|---|---|
| 配置与启动 | 合法配置、提交生效、拒绝与修正、模式进入 | 通用读写/访问属性按规则归组；改变业务的配置在相应场景验证效果 |
| 正常业务与生命周期 | 接入、处理、完成、退出及身份关联 | 检查阶段衔接；不按内部模块名称拆点 |
| 并发与顺序 | 独立业务进展、规定的仲裁顺序、用户隔离 | “老用户先”要说明候选资格，不能把被反压的既有命令当新仲裁 |
| 资源与恢复 | 合法耗尽、等待、释放、恢复、守恒 | 不同资源池按各自语义处理；细节不同的方向可保留独立目标 |
| 接口与反压 | 接收次数、字段稳定、恢复、不丢不重 | 同协议实例作维度；特殊语义另列检查或场景 |
| 复位与模式切换 | 旧事务处置、公开初值、新业务恢复 | 只检查规格承诺；不预设所有状态/载荷都清零 |
| 异常与恢复 | 有规定的非法输入响应、错误报告及恢复 | 合法激励与违规注入分开；无检测不等于应报警 |
| DFX 与中断 | 公开状态与业务一致、计数和清除副作用 | 独立副作用保留判据，普通字段取值可作维度 |
| 性能 | 端到端起止事件、负载、吞吐/延迟目标 | 内部阶段优化不能自行成为系统性能阈值 |

### 资源类场景的额外注意

“系统内部有 FIFO”不自动产生“每个 FIFO 的空满翻转”测试点。先说明外部如何积累未完成业务、限制哪条返回通路，以及资源不足会产生何种可见响应。合法输入上限由系统保证时，不要求 DUT 对超限输入自动反压、饱和或恢复。

同时区分取得资源、命令被接收、任务完成和资源归还。它们可能是四个不同事件，场景合并不能丢掉这些独立判据。

当资源许可在内部完成时，命令已出现可证明它此前取得许可，命令尚未出现却不能证明尚未占用资源。可以研究外部历史约束和竞争用户见证，但不能声称已精确重建每拍内部余额。由本模块规则推导的具体前序还要核对外部参与者合同；例如TS不等方向归还就可退休，不自动证明Router允许任意推迟归还。缺少该合同则标前序待确认，**方向耗尽恢复、原子分配等已有设计依据的测试点仍保留在主表**，不因当前构造未解决移为不计数候选。

## 8. 激励策略和度量

每个测试点都在“直接用例激励描述”中给出必要配置和值/约束、请求接口及字段、响应/推进顺序、预期和结束条件，未明确之处标 `需要 check`。具体写法见[激励描述规则](stimulus-description.md)。此项要求与主度量、平台是否具备能力无关。

先定主目标和维度，再选择策略：可以定向建立业务拓扑、随机化合法参数/返回间隔，并由端到端检查判定。不要因存在配置步骤就一律选择 `[t]`，也不规定随机/定向占比。

`[cg]/[cp]` 度量明确的场景维度及必要交叉；`[p]` 适合独立的边界协议性质，需证明真实触发；`[t]` 适合以规定序列及完成判据为主要证据的场景。复杂场景不能靠单个属性无报错声称全部完成。13 列中的主度量不限制实际使用其他辅助检查，写法见[字段合同](vplan-schema.md)。

## 9. 交付前的语义核对

- Register Access / Config Space / Dynamic Input / Performance 四类 base 已逐项检查；Cross 给出关联 item 和合法约束；Scenario 覆盖完整业务骨架。规格问题与 TP 阻塞视图一致，不重复计数。
- 主表足以评审场景目标，附录只补难以简述的前序或证明；共用的资源账本、环境约束和检查能力集中说明，不逐点重复。
- 不查看 LLD 内部图，也能根据场景说明判断要验证什么。
- 能沿“模式—典型业务—结果不同的分支”找到基础场景及结束条件；最小合法业务有显式落点，没有藏进配置范围或综合压力的参数列表。
- 完成、资源、身份、退出等判据已挂回相关业务；业务分支分别采证，没有用多个专项检查单独通过替代整条业务完成。
- 目标与设计职责及范围一致，控制模块没有被要求验证它不处理的数据结果；输入构造与观察不足记录为实施缺口，未反向裁剪目标。
- 合并后的每个主目标仍有判据和覆盖目标；不会把“整条链跑通”当成资源分配正确的全部证据。
- 无需求因为迁移而消失；只有实现细节的内容已映射外部行为或明确转交。
- 未决规格、平台能力及纯内部结构的范围归属可区分；有设计依据的业务点即使不能准确check也保留，规划完整性不以当前执行能力为门槛。
