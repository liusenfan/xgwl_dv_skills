# TS：先组织业务通路，再展开检查和覆盖

用于说明分解方法，不是已批准的 TS 全量测试点或对旧表的逐条审核。下列业务语义对应本次讨论选定的 LLD 正文；正式生成须重新核对用户指定的规格及冲突处理，不把此例当成独立设计依据。[局部规格](ts-spec-excerpt.md) 和 [六个场景的填写示例](ts_st_tp.md) 仅演示 ACK/Credit/生命周期专项的字段与粒度，不能作为业务目录或全量分解的起点。

本页展开新版 `Scenario` 内的业务组织方法；完整输出还须完成 Register Access、Config Space、Dynamic Input、Performance 和 Cross，不能将本页当成全部 Sheet 大纲。

## 1. 模式—业务—分支的基础骨架

先分清层级：Normal/Special 是工作模式；Broadcast DataIn、P2P DataIn、DataOut、Bypass、Reduce 和普通任务执行是业务通路；Reissue 是影响搬入/配对搬出执行集合的控制属性；单 Task、任务链、用户数和返回时序则描述规模与执行条件。

| 模式/阶段 | 典型业务或分支 | 独立可验收的业务闭环 |
|---|---|---|
| Normal | 单用户最小合法 Task 操作 | 接入/启动、命令身份与PC、目标单元接受、所需完成、正确退休；依据设计标出单Task适用类型及启动条件，未明确则待确认，不补造任意类型都可单独启动的规则 |
| Normal | 多 Task 任务链 | 接入、各类任务按依赖执行、等待唤醒及后继推进、全链完成、用户退出 |
| Normal | Broadcast DataIn，reissue=0 | 搬入执行、ATTR配对搬出跳过、剩余任务继续并正确结束 |
| Normal | Broadcast DataIn，reissue=1 | 搬入执行，配对搬出按任务链执行，完成后退出 |
| Normal | P2P DataIn，reissue=0 | 搬入和配对搬出均跳过，不产生对应搬入命令，剩余链正确推进并结束 |
| Normal | P2P DataIn，reissue=1 | 搬入执行，配对搬出按链执行，完成后退出 |
| Normal；Special中按合法链确认 | DataOut | 到达搬出任务、满足适用的方向许可、输出正确身份/PC/实际PID及VCID、完成；区分方向归还与用户退出，不预设两者固定先后 |
| Normal；Special中按合法链确认 | Reduce | 取得RMEM许可、发出任务、Core/DSA双ACK完成；RMEM返回只恢复空间，检查后续Reduce许可及退休/重生门控 |
| Special | 首Trigger启动与槽位任务链 | 首个接受的Trigger激活N个Task0；按配置执行单元发出，Task0有效完成后绑定UID，继续后继链 |
| Special | 每笔Trigger的DTE Bypass | 每笔已接受Trigger独立产生Bypass，检查保留SID/TID、Trigger UID/PID、DataIn PC；其ACK不推进槽位任务链 |
| Special | 槽位重生 | 已绑定的头用户全链完成、RMEM归还后在原SID重新开始Task0；重新绑定身份并回到年龄队尾，无普通Router用户退休通知 |
| 运行前阶段 | 权重加载 | 配置加载PC、发起DTE请求、保持至接受；完整加载结束和业务切换仅在外部完成协议明确后给确定判据 |

以上是场景族及分支索引，不要求一行恰好生成一个测试点，也不构成固定数量配额。Broadcast/P2P的四种执行结果必须分别有明确判据和完成证据；仅写“覆盖reissue=0/1”不足以替代这些业务路径。Special的Bypass和槽位任务链需要分别记账，首Trigger同时关联两条路径，后续Trigger不得重启整批槽位。

### 从基础业务扩展

1. 先建立最小合法业务和代表任务链，各自明确启动、应有/禁止命令、完成和结束状态。
2. 再增加同一业务多用户、任务链跨单元、Future DataIn、动态PID影响后继路由等有意义的变体。
3. 再构造搬入/搬出/Reduce交叠、Special Bypass与槽位DTE任务竞争，并加入反压、ACK时序与资源等待。
4. 最后补充独立配置错误、接口性质、复位及资源风险场景，关联回受影响业务。

Normal以普通用户退休及所需资源处置作为闭环的一部分；Special以本轮完成和下一轮Task0重生为结束证据，不能要求它自然排空。TS边界只验证命令、调度和生命周期；Core/DSA内部计算结果属于其他边界。方向耗尽等目标依据设计列出，具体前序的Router约束另标待确认；尚未解决构造或准确检查方法，不影响目标保留在主表。

### 修正“单 Task 被合并进配置”的组织方式

“配置提交”中覆盖链长1，只能表明该配置边界被使用。若要验证单 Task 操作，应有可识别的完整目标，例如 `ts_single_task_operation`，将发出、接受、完成及模式规定的结束检查挂到该场景。原有配置提交、ACK协调、退休等专项可继续保留并共享检查器；不要求把这些专项删除或把全部规则重复抄进每条业务描述。

## 2. 双 ACK：先后顺序合并，内部结构证明转交

| 旧样例点 | 新组织 | 保留内容 |
|---|---|---|
| ts_bb_dual_core_first | ts_ack_coordination 的返回顺序维度 | Core先到不提前推进，收齐后完成 |
| ts_bb_dual_dsa_first | 同一场景的返回顺序维度 | DSA先到的对称行为 |
| ts_bb_dual_same_cycle | 同一场景的返回顺序维度 | 同拍完整返回，无须额外一笔ACK |
| ts_bb_ack_groups_parallel | 同一场景的并发版本/C3 | 一组等待不阻塞其他独立组 |
| ts_bb_ack_burst16 | 可作为完成协调的合法突发维度 | 上限内的无丢失、配对和完成；六点示例未完整展开此维度 |
| ts_bb_ack_pop_push | 先辨明设计目标，业务要求保留 | 若要求并发接入/完成不丢失，保留完整条件和判据，窗口证明待设计；只有FIFO指针等纯结构要求按范围另列 |

Core单ACK完成是不同的完成规则，不能在合并双ACK时无记录地删除。违规错序和溢出的响应也要按其独立输入合同评估，不混入正常双ACK的通过条件。

## 3. Credit：保留三个不同目标

| 目标 | 示例场景 | 为什么保留 |
|---|---|---|
| 多方向必须同时取得 | ts_credit_atomic | 要证明缺一路时不提前占另一路，需安排竞争用户观察 |
| 同用户已有方向不重复扣 | ts_credit_reuse | 要保持用户存活并耗尽剩余额度，检查后继能否继续 |
| 合法耗尽后可恢复 | ts_credit_recovery | 要区分方向归还与用户退休，再检查受阻业务恢复 |

方向、N值和相同规则的实例差异可成为维度；年龄仲裁、无关资源不互相阻塞等独立风险仍需检查。六点表只将部分无关资源进展用于原子申请的见证，不代表完整年龄优先验证已完成。

即使当前平台不能精确重建Credit余额，或“跨退休保留方向欠账”的具体前序待Router协议确认，原子取得、复用和耗尽恢复这些设计目标仍保留在主表。分别标“激励构造待设计/前序协议待确认/check精度待解决”，不能移成不计入总数的候选，也不能只保留一个较弱的“任务最终跑通”目标。

## 4. 用户生命周期：顺序和复用分开证明

`ts_bb_retire_all`、`ts_bb_retire_head`、`ts_bb_retire_pulse` 的关联判据可以归入按序退休场景：条件未齐不退休、年轻用户不越过队头、每个用户正确通知一次。

`ts_bb_single_reuse`、`ts_bb_ring_reuse`、`ts_bb_empty_tail` 可归入槽位循环复用：N和空/非空/回绕是维度，检查新身份和完整任务轨迹。此场景不以向新生命周期注入违规旧ACK来替代合法复用检查。

设计规定的竞争保护或退休行为完整保留，当前不能确认窗口命中则标证据待设计；不得仅保留普通顺序检查来替代竞争条件下的目标。纯内部Hold编码等结构性质按范围另行追溯，不能因需要辅助观察就将业务场景整体移出主表。

## 5. 如何判断整理是否成功

读者应能按Normal/Special定位典型业务和分支，回答每个基础场景如何开始、输出什么、等待哪些完成以及如何退出或重生。然后能够找到用于加强该业务的并发/资源/异常检查，无需先理解内部寄存器。合并前后的有效需求、检查和覆盖维度应有映射。点数减少是组织变化的可能结果，不是质量标准；六行专项填写示例不能作为其他功能或整个TS的数量配额。
