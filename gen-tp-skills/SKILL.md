# 系统黑盒场景测试点生成器

## 职责与边界

将设计文档中的功能、业务和约束转成可追溯的黑盒场景计划。**一行测试点对应一个有明确主目标的黑盒验证项（基础性质、功能交互或业务场景），包含关联检查项和覆盖维度。** 参数、实例、事件先后或内部实现分支不自动增加测试点行。

**测试点建立与平台搭建隔离。** 测试点及预期仅来源于用户指定的设计文档（需求、HLD、LLD、接口和寄存器规格）；平台现状、driver/checker能力、激励难度和观察精度都不决定是否列点。设计要求存在的黑盒场景完整保留，即使暂时无法构造、准确check或自动转换，也保留正式 TP_ID、完整条件、预期和来源；表达、脚本及平台缺口单独记录，不能删点、移出主表或缩减目标。

**分解起点是工作模式下的典型业务通路。** 执行顺序为：业务骨架先行 → 基础对象与关系扫描 → 详细分解 Scenario → 双向补漏。基础扫描完成指对象和定义已检查、缺口已有去向，不要求所有疑问已解决；局部缺口不阻挡独立场景继续。不能只按配置、仲裁、ACK、Credit、退休等功能环节列点，使完整业务分散后无处独立验收。

系统边界由项目确定：既可以是芯片系统，也可以是作为整体被验证的子系统或模块。先明确包含哪些组件、外部参与者、可驱动接口和可观察结果；不能仅凭 `st` 文件名推定边界。若 TS 整体是 DUT，命令身份、调度顺序、完成及资源归还是主要结果，不臆造 TS 本身不处理的数据计算结果。

依据设计文档提炼业务预期。LLD 用于理解机制、发现风险和约束；内部信号、流水级、状态编码用于解释设计行为，不机械展开成内部结构测试。不能准确观察的业务要求仍列点。纯内部结构证明按验证范围另行追溯，范围划分不能借平台限制排除业务场景。不读 RTL 或现有平台代码补造/裁剪规格；激励及check实现由后续验证方案处理。

TP 与 DV MAS 可并行开展，但职责分开：TP依据设计给出应验证的场景、判据和覆盖目标；DV MAS承接所需能力，TC实现用例。能力反馈只更新实施说明，不能反向删减测试点。生成TP不要求先读取或核验平台；计划不等于已经执行或覆盖。

## 测试点大纲

新建计划按三类组织：**base** 必查 Register Access、Config Space、Dynamic Input、Performance；**探索类**用 Cross 分析有关联/约束的交叉功能；**scenario 类**用 Scenario 完整分析业务场景。四类 base 不因采用场景方法而省略；没有设计需求或资料不足时分别给出不适用依据或规格待补充说明。先理解业务，再按主目标归类，不把每个参数机械拆点。

`Scenario missing-input` 维护设计矛盾、冲突、欠定义和疑似不合理项；`lifecycle missing-input` 是按 TP_ID 派生的设计内容缺口清单，不是 DUT 生命周期测试。主表仍保留受影响的设计目标，问题及关联记录不计入 TP 总数。分类边界、问题字段与文档状态规则见[测试点大纲](references/tp-outline.md)。

## 执行流程

1. **界定边界与有效依据。** 记录 DUT、外部接口、环境保证和验证范围。区分有效需求、实现解释、系统输入约束、旧版/删除内容及未决项；来源冲突不因文件名为 LLD 就自动覆盖 HLD。为采用的规则建立来源映射。
2. **建立典型业务骨架。** 仅从设计文档识别工作模式、业务通路、改变执行结果的业务分支及结束方式。先识别最小合法业务（例如单 Task）和典型任务链的启动、输出、完成、退出或重生，形成待细化的业务骨架，不能仅以“链长=1”等配置维度代替基础业务闭环。前序尚未明确时保留目标并关联待确认项。
3. **扫描基础对象与关系。** 按[基础与关系检查](references/coverage-review.md)，在用户范围内逐项扫描四类 base、跨对象条件及行为；判定缺失前归并有效文档中可明确对应的定义，冲突保留双方来源。每项关联 TP、检查项、维度、问题或有依据的范围处置；不因典型业务未使用而遗漏，不把清单逐行机械变成 TP。
4. **详细分解 Scenario 并双向补漏。** 按[分类规则](references/tp-outline.md)形成独立业务目标，写清前置、配置与请求、交互、预期和结束条件；引用基础 TP 与通用约束，不能以关联清单替代业务验证。扩展有设计依据的分支、并发、反压、资源、异常及性能。单个 TP 只归一个主 Sheet；既检查业务所需基础项是否齐全，也检查基础要求是否有去向。允许带着明确待确认项推进，不要求全部 Base 定稿。
5. **写明必要激励并审核依据。** 每个测试点的“直接用例激励描述”均填写必要配置及值/约束、发起接口与请求、响应和推进顺序、预期与结束条件；不因主度量为 `[cg]/[cp]/[p]` 留空。不确定项在对应操作处标 `需要 check：具体问题`，区分规格未决与实施待设计，不能补造寄存器值或接口协议。 核对场景目标、设计条件和预期是否有文档依据；设计要求明确但前序构造、观察或精确check尚未解决时，完整保留在主表并标注待设计。规格冲突/缺失单独关联问题，不能把“不知道怎么测”推断成设计不可达，也不能把弱检查替代原目标。
6. **追溯并交接能力需求。** 将范围内设计要求映射到场景、判据和覆盖目标。按需向DV MAS交接所需激励、观察和检查能力，不把平台核对作为列点前置条件；路径未知写待设计，不编造实现名称。
7. **交付与复核。** 新计划按六类 TP 和两张问题表输出，详见[大纲](references/tp-outline.md)。保留单一测试点数据及规格问题源，lifecycle 视图由问题关联派生；问题行不计作 TP。保持完整附录，按用户最终选择交付 XLSX、HTML、Markdown 中的一种或多种；未指定格式时默认仅 XLSX。运行字段与统计校验，并核对所选格式保留全部内容。Excel 按规定的多 Sheet、英文列名及参考样式映射；旧表迁移须逐点确定主目标归属，不能仅改名或丢失业务层级。

分析允许往返细化；不以测试点总数减少作为完成标准。

## 核心决策

- **业务闭环优先：** 明确模式、入口、典型输出、完成条件和结束状态，再组织检查。单 Task、DataOut 等基础业务须有可定位的完整目标；ACK 顺序等变化可作该业务或专项完成协调场景的维度。
- **明确观察边界：** 握手稳定、公开寄存器复位值/访问副作用及明确性能承诺可以独立验证；纯内部 FIFO 指针、非公开状态寄存器清零不直接进入黑盒主表。设计要求的外部交互即使依赖精确窗口仍保留目标，命中证明或精确检查待设计。
- **Register Access 聚焦寄存器属性：** 模块级该页验证复位、访问权限、字段掩码、读写副作用及访问限制；APB只作为合法访问手段，不在该页展开总线协议、传输时序或错误响应测试。寄存器访问后的业务效果归 Config Space/Cross/Scenario，详见[寄存器验证边界](references/tp-outline.md#register-access-的模块级边界)。
- **分开三种关系：** 场景包含检查项；维度包含合法取值/组合；多个场景可由同一用例实现。场景不等于用例、单个 bin 或每条内部设计规则。
- **策略服务于目标：** `coverage_strategy` 明确主方法及简短选择理由：断言检查已定义的状态/时序性质，功能覆盖率统计取值、场景和交叉命中；复杂结果可用参考模型或记分板检查。需要时组合使用，不能以覆盖率命中替代正确性检查，也不按 Sheet 固定方法。详见[策略选择](references/vplan-schema.md#断言与功能覆盖率的选择)。允许定向建立前置再随机变化参数，不因场景有步骤就全部标 `[t]`，也不强制随机比例。
- **面向评审写作：** 用精简但明确的描述写条件、目标和判据；激励只展开必要配置、接口操作及关键顺序，未知项就地关联问题。共享配置可用具名基线引用，但每行仍须写场景专属值、请求及判据，不能只写“按规格配置/见附录”。长配置表放附录，不生成 UVM 代码或平台调用步骤。
- **保留用户分类与修订资产：** 新计划采用约定的六类大纲；旧表原样转换保留分类，授权迁移时将原业务分类保存在子分类或映射中；范围遗漏单列说明。合并需保留需求、检查、覆盖目标和旧点映射，不覆盖用户修改或擅自清除真实用例关联。
- **输出约定：** 格式由用户决定，支持 XLSX / HTML / Markdown 多选，未指定时输出 `<dut>_st_tp.xlsx`。仅交付选中的格式；工作用 Markdown 可作内部校验载体，不强制成为交付件或优先于用户编辑的 Excel。用户指定命名优先；`ut/it` 若表示实际内部验证需求，明确超出本技能职责。

## 不确定性与完成标准

有设计依据的验证目标即使暂时不可执行或无法准确check，也保留在主表和规划总数中。规格尚未明确的预期标待确认并关联问题，不猜测数值或响应。只有无法识别任何设计验证目标的纯问题才仅列缺口。已有规划路径可标“规划”；未有执行和充分检查证据不能标“已覆盖”。

**文档状态按内容完整性判断：** 目标、必要条件与激励、预期判据、覆盖要求及来源齐全标 `complete`；影响这些内容的规格或描述缺口未解决时标 `draft`。平台、表达或转换待办不影响内容完整性；`complete` 不代表已人工评审、执行通过或覆盖完成。每条 `draft` 必须在 `verification_goal` 末尾简述具体原因和问题 ID，并在 missing-input 表说明受影响范围与完成条件；归组点不能只写“部分待确认”。记录方式见[测试点大纲](references/tp-outline.md)。

完成时应满足：

- 每行直接用例激励描述均能回答“配置什么值、从哪个接口发什么、如何推进、预期什么、何时结束”；未知项明确标 `需要 check`。每行说明“设计要求在何种业务条件下验证什么”，完整保留预期判据；尚未实现或不能准确check的部分有明确标注，不削弱主目标。
- 四类 base 均有适用性结论；基础对象和关系逐项有去向，归组不丢判据。Cross 有完整条件和预期，取值覆盖对应行为，不做无依据全组合。
- 设计问题可追溯至来源及受影响 TP；两张 missing-input 表不重复维护问题正文，不把内容完整状态当作人工评审、仿真或覆盖结论。
- 有设计依据的典型模式与业务通路均有可识别的基础闭环，结果不同的分支有各自目标；未知前序/判据保留待确认，明确不适用项另记设计依据。
- 参数变化与检查项不机械拆行，独立风险未被大而全的压力场景掩盖。
- 范围内需求可追溯到检查项/覆盖维度，内部验证项及规格缺口有明确去向。
- 平台能力未知、激励困难、观察不足均未造成测试点删除、移出主表或验证目标缩水。
- 场景与统计一致，所有选中格式的点名、字段及附录一致；Excel 核对导出值和视觉排版。结构校验通过不代表语义正确、用户批准或覆盖收敛。

只在用户授权范围内写文件；已有授权无需重复确认。若约定逐节评审则按约定停下。工具失败报告受影响产物，不自动修改其他 skill、运行仿真、提交代码或发布外部消息。
